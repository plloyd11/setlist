<objective>
Fix two major bugs in the setlist builder: janky/crashing drag-and-drop reorder (UAT test 9) and intermittent song removal failure (UAT test 10).

Purpose: Both bugs share a root cause -- an unguarded $effect that overwrites optimistic client state when data props change during async operations. The server's delete-all + re-insert pattern in saveOrder compounds this by churning row IDs, breaking client-side new-item detection.

Output: Stable drag-and-drop reorder and reliable song removal with no race conditions.
</objective>

  <name>Task 1: Fix server saveOrder and removeSong to preserve row IDs</name>
  <files>src/routes/(app)/setlists/[id]/+page.server.ts</files>
  <action>
  Replace the delete-all + re-insert pattern in saveOrder (lines 98-112) with a stable upsert strategy:

  1. In `saveOrder`: Accept `items` as `Array<{ id?: string; song_id: string; position: number }>`. For each item:
     - If `id` is provided (existing row): UPDATE the position for that row using `.update({ position }).eq('id', item.id).eq('setlist_id', params.id)`
     - If `id` is NOT provided (new song from library): INSERT a new row with `{ setlist_id, song_id, position }`
     - Before upserting, delete any rows whose IDs are NOT in the incoming list (songs that were removed during reorder or items that no longer exist). Do this with a single query: `supabase.from('setlist_songs').delete().eq('setlist_id', params.id).not('id', 'in', '(existingIds)')` where existingIds are the items that have an `id` field.
     - Return the full set of rows after save so the client can sync IDs: `.select('id, position, song_id, songs(id, title, duration_seconds)').eq('setlist_id', params.id).order('position')` -- do this as a separate query after the mutations.

  2. In `removeSong` (lines 166-196): Remove the re-normalization logic (lines 177-193) that deletes all remaining rows and re-inserts them. Just delete the single row and update positions with individual UPDATE calls for remaining rows, OR simply leave positions with gaps (they only need to be ordinal, not contiguous -- the client assigns position from array index on next save anyway). The simplest correct fix: just delete the row (line 175) and return. No re-normalization needed.

  Why: The delete-all + re-insert pattern generates new UUIDs for every row on every save, making the client's ID-based new-item detection permanently unreliable. Preserving IDs eliminates the root cause of song duplication.
  </action>

  - removeSong just deletes the single row without re-inserting remaining rows
  </verify>

<task type="auto">
  <name>Task 2: Guard $effect and remove invalidateAll from mutations in +page.svelte</name>
  <files>src/routes/(app)/setlists/[id]/+page.svelte</files>
  <action>
  Three changes to +page.svelte, addressing the root cause of both bugs:

  **Change 1: Add isMutating guard to setlistItems $effect (lines 64-72)**

  Add a module-level `let isMutating = $state(false)` flag. Wrap the setlistItems $effect:

  ```
  $effect(() => {
    // Read data.setlistSongs to track the dependency
    const serverItems = data.setlistSongs;
    // But only sync if we're not in the middle of an optimistic mutation
    if (isMutating) return;
    setlistItems = serverItems.map((ss: any) => ({
      id: ss.id,
      song_id: ss.song_id,
      title: (ss.songs as any).title,
      duration_seconds: (ss.songs as any).duration_seconds,
      position: ss.position
    }));
  });
  ```

  **Change 2: Stop calling invalidateAll() after persistOrder and removeSong**

  In `persistOrder` (line 130): Remove `await invalidateAll()`. Instead, if the server returns the saved rows (from Task 1), update setlistItems from the response to sync IDs for newly inserted items. If response parsing is too complex, simply trust the optimistic state -- the next page load will sync. Set `isMutating = true` before the fetch, and `isMutating = false` in a finally block.

  In `handleRemoveSong` (lines 157-176): Remove `await invalidateAll()` from both success (line 170) and error paths (line 174). Set `isMutating = true` before the optimistic removal, set `isMutating = false` after the fetch completes. On error, revert by calling `invalidateAll()` AND setting `isMutating = false` so the $effect can re-sync from server.

  In `handleAddSong` (lines 138-154): Keep invalidateAll() here since there's no optimistic state to protect -- but wrap with isMutating guard: set `isMutating = true` before fetch, `false` after invalidateAll completes.

  **Change 3: Use song_id for new-item detection in handleSetlistFinalize (lines 89-114)**

  Replace the existingSetlistSongIds check. Instead of comparing item.id against data.setlistSongs IDs, detect new items by checking if the item has a `song_id` that matches `item.id` (library items arrive with id = song.id, while setlist items have id = setlist_songs UUID which differs from song_id). The reliable test:

  ```
  const isNewFromLibrary = !item.song_id && !item[SHADOW_ITEM_MARKER_PROPERTY_NAME];
  ```

  When a library item is dragged, it arrives as a LibraryItem (which has no `song_id` field -- it IS the song). So check: if `item.song_id` is undefined/falsy and it's not a shadow, it's new from library. Assign `song_id: item.id` and a new UUID for `id`.

  Also send the existing row `id` in persistOrder's payload so the server can do upserts:
  ```
  items.map((item, index) => ({
    id: isNewFromLibrary ? undefined : item.id,
    song_id: item.song_id,
    position: index
  }))
  ```

  Why these changes together: The unguarded $effect is the single mechanism causing both the DnD jank (resets mid-animation) and the remove-song race (restores removed song from stale data). Removing invalidateAll from mutations means the $effect won't fire during async windows. The isMutating guard is a safety net for any other data changes. Using song_id for detection eliminates the ID-churn false positives.
  </action>
