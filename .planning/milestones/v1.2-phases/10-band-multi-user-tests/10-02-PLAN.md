**RLS-01: Song isolation**
```
test.describe('Song data isolation (RLS-01)', () => {
```
- Test: "should not show another user's songs in the song library"
- Create a song for User A (worker-scoped primary user) via `createSong(page, testUser.id, { title: 'User A Private Song' })`
- Create User B via `createSecondUser(browser)`
- In try/finally (finally: userB.cleanup()):
  - User B navigates to `/songs`
  - Assert `getByText('User A Private Song')` is NOT visible (use `expect(...).not.toBeVisible()` or `expect(...).toHaveCount(0)`)
  - This validates the songs table RLS policy filters by user_id

NOTE from research: There is no `/songs/[id]` route, so direct URL navigation is not possible for songs. The CONTEXT decision says "direct URL navigation" but research found songs have no individual detail page. Test via the list page instead -- this still validates RLS because the songs table SELECT policy uses `auth.uid() = user_id`.

**RLS-02: Setlist isolation**
```
test.describe('Setlist data isolation (RLS-02)', () => {
```
- Test: "should block access to another user's setlist via direct URL"
- Create a setlist for User A via `createSetlist(page, testUser.id, { name: 'Private Setlist' })`
- Create User B via `createSecondUser(browser)`
- In try/finally (finally: userB.cleanup()):
  - User B navigates directly to `/setlists/${setlist.id}` via `userB.page.goto()`
  - RLS blocks the query -- the server load gets null and should show error or empty state
  - Assert User B does NOT see "Private Setlist" text: `expect(userB.page.locator('body')).not.toContainText('Private Setlist')`
  - Also verify the page shows some indication of not-found (check for error text or redirect away from the URL)

**RLS-03: Unauthenticated shared setlist access**
```
test.describe('Unauthenticated shared access (RLS-03)', () => {
```
- Test: "should allow unauthenticated user to view a shared setlist"
- Create a setlist for User A, enable sharing via admin API: `adminClient.from('setlists').update({ share_token: crypto.randomUUID() }).eq('id', setlist.id).select().single()` to get the token
- Open unauthenticated context: `browser.newContext({ storageState: undefined })`
- In try/finally (finally: context.close()):
  - Navigate to `/share/${shareToken}` -- assert setlist name is visible
  - This confirms anon SELECT policy on shared setlists works

- Test: "should block unauthenticated user from accessing protected routes"
- Using the same unauthenticated context pattern:
  - Navigate to `/dashboard` -- assert redirected to `/auth`
  - Navigate to `/songs` -- assert redirected to `/auth`
  - This confirms auth guard blocks unauthenticated access to non-share routes

**RLS-04: Band membership enforcement**
```
test.describe('Band membership enforcement (RLS-04)', () => {
```
- Test: "should block non-member from accessing band data"
- Create a band for User A via `createBand(page, testUser.id, { name: 'Members Only Band' })`
- Create User C (non-member) via `createSecondUser(browser)` -- naming as userC per CONTEXT decision about third user
- In try/finally (finally: userC.cleanup(), safeDelete('bands', band.id)):
  - User C navigates to `/bands/${band.id}` via `userC.page.goto()`
  - The band layout.server.ts throws `error(404)` because RLS blocks the band query (returns null for non-members)
  - Assert error page: `expect(userC.page.getByText(/not found/i)).toBeVisible()`
  - IMPORTANT per research Pitfall 7: Expect 404 error page, NOT a redirect

Each test must use try/finally for cleanup. Use unique test data values (faker or descriptive strings) to avoid parallel test collisions.
