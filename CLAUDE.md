# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

Setlist — a web app where bands and musicians manage song libraries and build timed setlists. Users add songs (name + duration), drag them into setlists to see running totals against a target time, and share setlists via public links or band workspaces. Setlists can also include timed **gaps** (labeled breaks between songs) that count toward the total. **Practice** is a separate main-menu destination for shedding songs, warm-ups and working on skills; **Rehearse** is different, and runs a set top to bottom. Bands additionally get a **Demos workspace** for work-in-progress recordings: members upload versioned audio, organize it into nestable folders, and leave timestamped comments on a waveform player.

**Naming notes:** the UI says "Techniques", but its tables (`skills`, `skill_tempo_logs`) keep the original name. The feature is "Demos" everywhere users see it (nav, page copy, `/bands/[id]/demos` routes), but the DB tables (`tracks`, `track_versions`, `track_comments`, `track_folders`), RPCs, the `tracks` storage bucket, `src/lib/components/tracks/`, `src/lib/server/tracks.ts`, and type names intentionally keep the original `tracks` vocabulary — renaming them would churn RLS policies, RPCs, and storage paths for zero user value. Don't "fix" this inconsistency. Old `/bands/[id]/tracks` URLs 301-redirect to `/demos`.

## Commands

Uses **pnpm** (pinned via `packageManager`), Node >= 22.17 (`.nvmrc` pins 24 for CI and Netlify).

```sh
pnpm dev                 # Vite dev server
pnpm build               # Production build (Netlify adapter)
pnpm verify:server       # After a build: load every server chunk as strictly as Netlify does
pnpm check               # svelte-kit sync + svelte-check type checking
pnpm lint                # Prettier check (no ESLint in this project)
pnpm format              # Prettier write
pnpm test                # Playwright E2E suite (requires .env.test — see below)
pnpm test:ui             # Playwright UI mode
pnpm test:cleanup        # Delete stale e2e-* test users from Supabase

npx playwright test tests/songs.spec.ts        # single spec file
npx playwright test -g "creates a setlist"     # single test by title
```

### E2E test requirements

Tests run against a **real Supabase instance** (no mocks) and mutate live data. They require a `.env.test` file with `PUBLIC_SUPABASE_URL`, `PUBLIC_SUPABASE_PUBLISHABLE_KEY`, and `SUPABASE_SERVICE_ROLE_KEY`. Playwright auto-starts the dev server on port 5173. CI (`.github/workflows/ci.yml`) intentionally runs only check/lint/build/verify:server with placeholder env vars — the test suite is local-only.

## Architecture

**Stack:** SvelteKit 3 + Svelte 5 (runes), Vite 8, TypeScript 6 strict (Kit and svelte-check don't support TS 7 yet), Tailwind CSS v4, Supabase (Postgres + Auth + RLS), `svelte-dnd-action`, deployed to Netlify.

### Auth & routing

- `src/hooks.server.ts` creates a per-request Supabase server client (`@supabase/ssr` with cookie handlers) and a **memoized `safeGetSession()`** on `locals` (getUser() is a network call; guard + layouts all share one promise). It also enforces the auth guard: everything is protected except `/auth/*`, `/share/*`, and `/`.
- `/` redirects logged-in users to `/dashboard` (marketing landing page for logged-out visitors).
- **Cache safety:** the root layout serializes the session and cookies into every page, so `handle` rewrites any `public`/`s-maxage` response to `private, no-store` when the request carried cookies, and applies the no-store headers `@supabase/ssr` passes to `setAll` on token refresh. Regression coverage is in `tests/security-regressions.spec.ts`.
- **Redirect targets** from query params or cookies go through `safeInternalPath` (`src/lib/utils/safeRedirect.ts`). Don't hand-roll prefix checks: browsers strip tabs and newlines, so `/\t/evil.com` passes them.
- `src/routes/(app)/` is the authenticated app (dashboard, songs, setlists, bands, settings). `/share/[token]` is the public read-only setlist view. `/auth` handles Google OAuth (PKCE) and email/password sign-in.
- `src/routes/+layout.ts` creates the browser/server Supabase client used client-side; invalidate with `depends('supabase:auth')`. Public env vars are declared in `src/env.ts` and imported from `$app/env/public`; there is no `svelte.config.js` (Kit config lives in the `sveltekit()` plugin in `vite.config.ts`), and imports use `#lib/...js` rather than `$lib`.

### Data layer

- **There is no API middleware — Supabase RLS is the authorization layer.** Page `+page.server.ts` loads query through `locals.supabase` (user-scoped, RLS-enforced). Schema and policies live in `supabase/migrations/`.
- Band access control flows through a `user_band_ids()` security-definer Postgres function referenced by all band RLS policies.
- Band shared songs use a **junction table referencing the original song row** — edits sync automatically, no duplication.
- TypeScript row types are hand-maintained in `src/lib/types/database.ts` (not generated) — keep in sync with migrations.
- Durations are stored as integer seconds; parse/format via `src/lib/utils/duration.ts` ("mm:ss" strings).
- **Dashboard** (`/dashboard`, called Home in the nav; `src/lib/components/dashboard/`): gig dates mean the day where the musician is, and Netlify runs on UTC, so the page keeps their zone in a `tz` cookie and the load works out `today` from it (`todayInZone` in `src/lib/utils/gigDate.ts`). Without that, tonight's gig falls off the board on a US evening. Its Share button posts to the set's own `?/toggleShare` action, personal or band.
- **Set totals:** the running total has one rule, in `src/lib/utils/setlistTiming.ts`: transitions apply only between consecutive songs. Anything showing a set's total (dashboards, setlist lists) goes through `summarizeSetlistRows`, with rows ordered by position, so every screen shows the same number as the TimingBar and Rehearse. Regression coverage is in `tests/ux-regressions.spec.ts`.
- **Member names:** a `profiles` row doesn't exist until someone saves it in Settings, so a missing name means "hasn't set one", not "left the band". Show names through `memberName()` (`src/lib/utils/memberName.ts`).
- **Setlist gaps:** a `setlist_songs` row is either a song reference (`song_id` set, `gap_seconds`/`gap_label` null) or a timed break (`song_id` null, `gap_seconds` > 0, optional `gap_label`) — enforced by the `setlist_songs_song_or_gap` check constraint. Reordering goes through the `save_setlist_order(setlist_id, items)` security-definer RPC, which serializes concurrent saves and re-validates song visibility.
- **Demos** (band WIP-audio workspace; DB vocabulary is `tracks` — see naming note above): audio uploads go **client-side direct to the private `tracks` Storage bucket** via a signed upload URL (Netlify's ~6 MB function body limit rules out proxying), then the atomic `create_track_version()` RPC records the metadata row. Each upload is an immutable `track_versions` row (path `bands/{band_id}/tracks/{uuid}.{ext}`); comments attach to a specific version. Playback uses a server-minted **signed URL** (6h TTL) through the user-scoped client, so RLS gates access before a URL exists. Bucket: 50 MB/file limit, audio MIME allowlist. Server-side metadata validation in `src/lib/server/tracks.ts`.
- **Client-side audio compression** (demos + song audio variants, via `AudioUploadZone`): lossless picks (WAV/AIFF/FLAC) and lossy files over the 50 MB bucket cap are re-encoded to 192 kbps MP3 in the browser before the storage PUT — lamejs in a Web Worker (`src/lib/utils/audioCompress.ts` + `mp3Encoder.worker.ts`), reusing the AudioBuffer already decoded for waveform peaks. This is why FLAC/AIFF are accepted as input despite being absent from the bucket MIME allowlists (raw lossless never reaches storage), and why the pick cap (250 MB, `MAX_SOURCE_FILE_SIZE`) is larger than the bucket limit. There is deliberately no server-side transcode path — Netlify's body limit rules it out.
- **Song attachments:** songs carry **rehearsal audio variants** (`song_audio`, private `song-audio` bucket — e.g. "Full mix", "No guitar") and **charts/tabs** (`song_files`, private `song-files` bucket — PDF, Word, Guitar Pro). Both follow the same model: owner uploads/manages, anyone who can see the song (owner + band members via `band_songs`) can read; storage paths are CHECK-constrained to `songs/{song_id}/%`; only `label` is mutable (column grant). Uploads are client-side direct to storage (same Netlify limit rationale as demos); server validation in `src/lib/server/songAudio.ts` / `songFiles.ts`. **Guitar Pro files have no registered MIME type**, so the `song-files` bucket allowlist includes `application/octet-stream` and the real gate is the extension allowlist (`chartUpload.ts` client-side, `songFiles.ts` server-side) — don't "tighten" the bucket list without checking that.
- **Rehearse vs Practice:** keep these apart. `/setlists/[id]/rehearse` is for running the set: it plays it top to bottom (state machine in `src/lib/components/rehearse/rehearseState.svelte.ts`). Don't add shedding tools there. Practice lives under `/practice`: Today (a session fitted to the time you say you have, by `src/lib/utils/sessionPlan.ts`), `warm-up` (a timed routine of exercises), `shed` (song list), `techniques` (lessons, drills and a tempo log) and `log`. Its practice screens are `/songs/[id]/practice`, `/demos/[id]/practice` and `/exercises/[id]`, all built on `src/lib/components/practice/ShedScreen.svelte`: audio, loop and speed controls, charts, metronome (`?from=` carries the back link, validated as an internal path). All Practice data is private to the musician, even for band songs. Demos have no link in practice history (`practice_session_items` has no track column), so their time logs under the title alone, as `kind: 'song'`. Time is tracked by `practiceTracker.svelte.ts`, which journals to localStorage and posts running totals to `/practice/session`, so closing the tab loses nothing. Curated lessons live in `src/lib/practice/curatedTechniques.ts`.
- **Tab player:** Guitar Pro and TuxGuitar files open in `src/lib/components/practice/TabPlayer.svelte` (alphaTab), via `ChartList`. The library loads only when a tab opens. Its Vite plugin copies the font and SoundFont into `static/`, which is git-ignored. The screen is built from `SongPracticePanel`, whose `arrange` snippet lets a page lay out its strip, player and controls. alphaTab can't read `.tg`, so `src/lib/utils/tuxguitar/` converts it to alphaTab's score: the zip and XML format from TuxGuitar 1.6 on, and the binary 1.3 to 1.5 layout. Older files fail to the download link. `src/lib/utils/tabSoundSync.ts` holds the cursor back by the device's output latency, because alphaTab's position runs ahead of the speakers (about 250 ms on Bluetooth).
- **Metronome:** `src/lib/utils/metronome.ts` schedules clicks ahead on the Web Audio clock, because JS timers drift. `src/lib/components/practice/Metronome.svelte` remembers tempo per song in localStorage. Both sign URLs server-side through the user-scoped client and share the remembered per-song variant choice via `src/lib/utils/variantChoice.ts` (localStorage).
- **Rig** (practice screens): plays an audio interface's input into the same headphones as the track, so practicing with an amp needs no DAW. It has two modes, and each keeps its own input channel, gain, cuts, level and IR, so swapping is one tap. **Real amp** is a head into a load box, through a cab IR. **NAM** is a guitar plugged straight in, through a Neural Amp Modeler model (and an IR, unless the model is a full rig). `src/lib/utils/rig.svelte.ts` is one engine for the whole app, so monitoring carries on between screens. `RigPanel.svelte` sits beside the metronome in `ShedScreen`. Off those screens, `RigIndicator.svelte` in the app layout shows "Rig on" with a switch. It's all per browser, with no migration: settings in localStorage, IRs and `.nam` models in IndexedDB (`src/lib/utils/rigStore.ts`). A rig belongs to one machine, and so do its device IDs. NAM runs on TONE3000's `neural-amp-modeler-wasm` (MIT): the real NAM C++ engine as wasm in an AudioWorklet, imported lazily and only from `neural-amp-modeler-wasm/engine`. The package root is a React player and would pull React in, which is why React sits in node_modules as its peer and never ships. It's excluded from `optimizeDeps` because it finds its worklet and wasm beside itself. A standard model costs about 13% of one core on an M4 Mac (measured by rendering one offline), and adds no latency. Model loudness is evened out to -18 dB, as the NAM plugin does, capped at ±20 dB. NAM doesn't resample, so the panel warns when the model's rate differs from the interface's. **TONE3000** (`src/lib/utils/tone3000.ts`, `tone3000Browser.svelte.ts`, `Tone3000Browse.svelte`): both pickers can browse TONE3000 through its Select flow. TONE3000's own window does the browsing, and OAuth with PKCE runs entirely in the browser. The window comes back to `/auth/tone3000`, which passes the answer to the page that opened it and closes. Tokens stay in memory for one pick and are never stored. Amps are A2 captures only (`architecture=2`), by Pete's choice; IRs are `format=ir`, `gears=cab`. It needs `PUBLIC_TONE3000_CLIENT_ID` (a publishable key), and hides without it. Its API terms ask for "Powered by TONE3000", downloads only when someone asks, and the creator and license kept with each file, which is why `RigFile.source` exists. The free tier is for non-commercial products only, so check the terms before Setlist charges for anything. The e2e test fakes TONE3000 with `context.route`. Keep `echoCancellation`, `noiseSuppression` and `autoGainControl` off: Chrome's call processing wrecks guitar and adds latency. Monitoring is never restored on reload, like the loop. A built-in mic into built-in speakers is refused, because it feeds back. Playing through the rig counts toward the practice clock. It's judged on pick attacks (`src/lib/utils/attackDetector.ts`), not on level, so an idle amp's hiss never keeps the clock running. Chrome on a Mac measured fine with a load box into a MOTU M4. If latency ever matters more, the next step is a native shell, not a rewrite.
- **Rig page** (`/rig`, in the main nav; `src/lib/components/rig/`): the same engine with room for the whole chain. The board is a rack the signal runs down (Input, Amp in NAM mode, Cab, Output), with a meter where each end can go wrong: Clip on the input, Limit on the output (the limiter's own `reduction`). Don't fork the engine for it: the page and `RigPanel` both drive `rig`, and share their readings through `src/lib/utils/rigFormat.ts`. **Saved rigs** are one mode's whole setup under a name (`practice:rig:presets:v1` in localStorage). Loading one switches to its mode and puts its settings there, so the two modes still each keep their own. Which one is "Loaded" is worked out by comparing, not remembered, so a turned knob un-loads it; saving under a name that's taken saves over it. The panel lists them in a select once there are any. The **library** is where models and IRs are renamed and removed (it asks first, and a removed file comes out of every saved rig). Files dropped anywhere on the page are sorted by extension; a batch is kept without being chosen, so the sound doesn't change on the way in. The page counts as a panel (`rig.panels`), so the "Rig on" chip stays off it, and `?from=` carries the way back to a practice screen. Tests: `tests/rig-page.spec.ts`.
- **Two IRs:** each mode's setup has `irId`, `irId2` and `irBlend`. Two convolvers run side by side, each into its own gain (`irShares`). The blend is a straight crossfade on purpose, not equal power: two IRs of one cab are mostly the same sound, so equal power would swell in the middle. One IR on its own is always all of the sound, wherever the blend sits. An IR sits in one slot: picking it for the other moves it. The second picker and the Blend knob are on the Rig page; the practice panel shows them only once a second IR is in. TONE3000 browsing carries the slot it was opened from (`tone3000.slot`).
- **IR sync** (`src/lib/utils/rigCloud.ts`, table `rig_irs`, private bucket `rig-irs`): IRs a musician uploads follow their account. IndexedDB stays the copy the rig plays from; `rig.sync()` brings it and the account into line (fetch, drop, rename, send up), on the first rig screen of a visit and each time the Rig page opens. The row's id is the id the browser keeps the file under, so settings and saved rigs point at the same IR on every device. `RigFile.owner` is the account a copy is in step with: that's how "removed on another device" is told from "not sent up yet". Renames and removals of a synced IR go to the account first, or the next sync would undo them. It's all written by the browser through the user-scoped client, so the rules are in the migration: RLS for whose, CHECKs for what. **Only uploaded IRs sync.** TONE3000's files stay on the device they were picked on (its free tier covers the picker flow, not keeping its files on our storage; its docs list library sync under full access), and so do amp models, settings and saved rigs. The app layout calls `rig.connect()` with whose account it is; nothing is fetched until a rig screen opens. Rig tests clear `rig_irs` for their user before each test (`cleanupRigIrs`), since a worker's tests share one account. Cross-user coverage is in `tests/rig-irs-rls.spec.ts`.
- **DAW practice controls** (practice page only): `WaveformPlayer.svelte` (wavesurfer.js v8) takes an opt-in `practice` prop — demos and rehearse consumers are unaffected — which registers the wavesurfer Regions plugin for a single drag-to-create A/B loop region. The loop engine lives in the `timeupdate` handler and triggers only on a **natural crossing of the B point** (`lastTick` delta check), so user seeks past B play through and re-trap on the next pass; the plugin's `region-out` event is deliberately not used (it also fires on backward seeks and on the engine's own jump). **Pre-roll (2 s)** rewinds before the loop's A point on the wrap, on arming from outside the region, and on every transport start inside the armed region (DAW semantics — pressing play includes the lead-in; clamped at 0:00). Speed is always pitch-preserved (`setPlaybackRate(rate, true)`). The page owns durable state and re-applies it via the player's `onready` on every variant remount; persistence is per song in `src/lib/utils/practicePrefs.ts` (volume, speed, loop, pre-roll, named sections — `loopEnabled` is deliberately **not** persisted so a reload never restores an armed loop trap). Keyboard map (`practiceShortcut` in `src/lib/utils/practiceKeys.ts`): Space, `L` (arm loop), `[`/`]` (pin loop points at the playhead), arrows (±5 s), `M` (metronome). Text fields and dialogs own every key, sliders claim theirs with `preventDefault`, and buttons and links keep Space. The rotary control is `src/lib/components/ui/Knob.svelte`; the control strip is `src/lib/components/songs/PracticeControls.svelte`. Loop region colors: chartreuse wash only while armed (live signal), surface wash when parked — matching the Limelight rule.
- **Demo folders** (`track_folders`): nestable band-shared organization (max depth 5, no cycles). Because "any member can organize" can't be expressed in the creator-or-owner column-grant RLS, structural mutations (create/rename/move/delete, reparent-on-delete) go through security-definer RPCs in `20260611000000_create_track_folders.sql`.

### UI patterns

- Setlist builder uses `svelte-dnd-action` with **copy-on-drag** from the library panel (library resets after drop) and **optimistic UI**: update local state immediately, sync via `fetch` + `refreshAll()`. Kit 3 returns `fail()` as a real HTTP failure status, so `response.ok` is a valid check on these raw `fetch` calls to form actions.
- Theme is DOM-based (inline script in `app.html` prevents FOUC), not store-driven; `src/lib/stores/theme.svelte.ts` wraps it.
- **Touch targets** are handled in `layout.css` under `pointer: coarse`, so desktop is unaffected: a button's hit area grows to 44px through `::after`, and fields get 44px height and 16px text (iOS zooms on anything smaller). Links opt in with `.hit-44`, because they can wrap nested buttons or sit in prose. A clipping parent (`overflow-hidden`, `truncate`) defeats the pseudo-element, so size those for real with `min-h-11` or `pointer-coarse:` variants.
- **Focus:** every control gets the Limelight outline from `layout.css`, so a missing `.focus-live` doesn't fall back to the browser ring.
- **Micro-labels** (the `text-label` token, uppercase) are for instrument readouts only. Form labels are `text-sm font-medium`.
- **Numbers:** neither Klima nor Cartridge has tabular figures, so `tabular-nums` does nothing. Readings that tick or stack in a column go through `src/lib/components/ui/Digits.svelte`, which gives each digit an equal slot and keeps one readable text for screen readers. Leave static display numbers alone: their natural spacing looks better.
- **Page frame:** every app page is full width with the same gutters, from the `page-frame` utility in `layout.css`. Don't give a page a max-width; keep prose and form fields readable inside the frame, and flow stacked sections into columns. See The Page Frame in DESIGN.md for the screens that frame themselves.
- **The stage** (`/` logged out, `/auth`, `/auth/update-password`): these pages live in the `src/routes/(stage)/` group, whose layout mounts one three.js scene, `src/lib/components/landing/StageScene.svelte` over `landing/stage/` (`scene.ts` assembles it, `gear.ts` builds the backline, `lighting.ts` the rig and beams, `textures.ts` draws every surface on a canvas). Because the scene is in the layout it survives navigation between them, and the page transition is the camera travelling from one page's shot to the other's (`poseFor` in `scene.ts`). The pages only fade their own content: out with `out:fade|global`, in with a CSS delay that applies once a link has been followed (`.travelled`), so a fresh load of `/auth` has its form ready at once. The auth pages sit in `StageCard.svelte`, beside the kit or under it; its media query and `SIDE_BY_SIDE` in `scene.ts` are the same test and must change together. `/auth/callback`, `/auth/confirm` and `/auth/tone3000` stay outside the group. Everything over the stage is styled dark in both themes. three.js is imported inside `onMount`, so it stays a lazy chunk that only these pages fetch. The platform runs far past both edges, so it reads full width on any screen. Beams are warm and cool only; Limelight stays a UI signal. Keep shader inputs clamped: one NaN from a beam (`pow` of a negative at a multisampled edge) goes through the bloom and blacks out the whole frame on Metal, but not in software rendering. **Software rendering gets the painted fallback, not the scene** (`hasGpu` in `StageScene.svelte`): on the CPU it holds the main thread so long that the sign-in form stops responding, which is also what the e2e suite's headless browsers would hit, since every worker signs in through `/auth`. So the suite never sees the scene; to look at it, launch headless Chromium with `--use-angle=metal --enable-gpu` and force `preserveDrawingBuffer` on, or the canvas comes out empty.
- **Tour** (`src/lib/components/tour/TourOverlay.svelte`, mounted in the app layout; steps and copy in `src/lib/utils/tour.ts`, state in `src/lib/stores/tour.svelte.ts`): a guided walk through Home, Songs, Setlists, Practice, Rig and Bands. Each step navigates to its page and lights the control marked `data-tour="…"`; a step whose anchor isn't on screen shows its card with no hole, so a page can change without breaking the tour. It's a native modal `<dialog>` (top layer, inert page, trapped focus, Esc), and one element's box-shadow is both scrim and hole. It measures the anchor every frame instead of listening for resize and scroll, because pages settle after they load. Step navigations use `goto(…, { reset: false })`: Kit's default blurs the focused control, which drops focus out of the dialog. "Seen" is `user_metadata.tour_seen` (once per account, no migration), written when the tour auto-starts. It only auto-starts on `/dashboard`, for accounts created after `TOUR_LAUNCHED_AT`. Replay is "Take the tour": the compass row in the rail, and a button in Settings (the rail doesn't exist on a phone). Don't name it "Replay tour": that contains "play", and a dozen specs find the transport by `getByRole('button', { name: 'Play' })`. `createTestUser` marks test users as seen; pass `tourSeen: false` for a real first visit.
- Components organized by domain: `src/lib/components/{bands,dashboard,landing,layout,practice,rehearse,rig,setlists,songs,tour,tracks,ui}/`.
- Prettier: tabs, single quotes, 100-char width, no trailing commas, Tailwind class sorting.

### Test infrastructure (`tests/`)

- `fixtures.ts`: **worker-scoped fixtures** — one test user per worker created via admin API, authenticated through the real UI once, `storageState` reused by all tests in the worker. Teardown deletes the user (CASCADE cleans up data).
- `helpers/supabase-admin.ts`: service-role client that bypasses RLS — used only by factories/cleanup, never in assertions.
- `helpers/factories.ts`: `createSong`/`createSetlist`/`createBand` insert via admin API (bypass UI when testing data, not workflow).
- `helpers/dnd.ts`: custom `dragAndDrop` using raw `page.mouse` — **Playwright's `locator.dragTo()` does not work with svelte-dnd-action**. Assert reorder results by comparing bounding-box y-coordinates.
- `helpers/multi-user.ts`: `createSecondUser(browser)` returns `{ page, user, cleanup }` for cross-user/band scenarios in separate browser contexts.
- Cleanup philosophy is warn-not-throw: stale data logs a warning instead of failing the run.
- **Rig tests** (`practice-rig.spec.ts` for the panel, `rig-page.spec.ts` for the page, `rig-irs-rls.spec.ts` for who can reach a synced IR): Chromium's fake capture device stands in for an interface, with `--use-fake-ui-for-media-stream` set per file. That flag counts as access already given, and headless Chromium has no real prompt (`getUserMedia` fails as not supported without it), so the first-visit test stubs `enumerateDevices` and `getUserMedia` to behave like a browser that hasn't been asked. TONE3000 is faked at the network by `helpers/tone3000.ts`. The account is put out of reach with `page.route` on the `rig_irs` table and bucket; Supabase's client retries a failed read for several seconds, so those waits are long on purpose. One test reads the level meters, since nothing else shows they're wired up: it asks only that they read while live, go dark when off, and fall when the gain is cut.
- **Audio playback is never asserted** — with one exception: `practice-loop-playback.spec.ts` plays real audio to exercise the loop engine. Two Chromium-under-Playwright quirks it works around (and that any future playback test must respect): media requests **abort if routed through `page.route` interception**, and a seek issued before first play stalls the element at `readyState 1` — so the spec rewrites `HTMLMediaElement.src` in-page to a local range-capable HTTP server, creates the loop region by dragging (no pre-play seek), and starts playback from 0.

## Design Context

Design work is governed by two root files (consumed by `/impeccable` and useful to any agent touching UI):

- **`PRODUCT.md`** — strategic context: register (`product`), users, brand personality ("stage-ready and confident"), anti-references (no generic SaaS dashboard, no Spotify clone, no corporate/enterprise), design principles, WCAG AA target.
- **`DESIGN.md`** — visual spec: "The Backline" north star, color roles (Backstage Navy surfaces, Tube Glow copper for actions, Limelight chartreuse strictly for live signals like focus/drop targets), Cartridge display + Klima body typography, glow-as-signal elevation, component doctrine. Tokens themselves live in `src/routes/layout.css`; DESIGN.md explains how to apply them.
